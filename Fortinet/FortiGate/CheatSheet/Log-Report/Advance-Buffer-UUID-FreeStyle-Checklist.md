# 1. Logging Architecture Checklist

### Understand the logging path

```text
FortiGate Event
      |
      v
   Logging
      |
      v
    miglogd
      |
      +----------------+
      |                |
      v                v
   Memory            Disk
      |                |
      +-------+--------+
              |
              v
       FortiAnalyzer
              |
              v
        SIEM / Analysis
```

### Architecture validation

* [ ] Identify where logs are generated
* [ ] Identify the configured log destination
* [ ] Verify local logging configuration
* [ ] Verify FortiAnalyzer connectivity
* [ ] Identify whether logs are buffered in memory
* [ ] Identify whether logs are buffered on disk
* [ ] Understand `miglogd` behavior
* [ ] Verify log forwarding status
* [ ] Verify log retention requirements
* [ ] Verify downstream SIEM/FortiAnalyzer ingestion

> **Golden Rule:** Troubleshoot logging from **event generation → local processing → buffering → forwarding → analysis**.

# 5. FortiAnalyzer Disk Buffer Checklist

When FortiAnalyzer becomes temporarily unavailable, local buffering can prevent immediate loss of logs.

### Architecture

```text
FortiGate
    |
    v
 Logging
    |
    v
  miglogd
    |
    +--> Memory Buffer
    |
    +--> Disk Buffer
            |
            v
      FortiAnalyzer
```

### Configure FAZ Disk Buffer

```bash
config system global
    set faz-disk-buffer-size 200
end
```

### Default Reference

```text
Default:
100 MB
```

Example:

```text
Configured:
200 MB
```

### Validation

* [ ] FortiAnalyzer logging is configured
* [ ] FortiAnalyzer is reachable
* [ ] Disk buffering is configured when required
* [ ] Buffer size is appropriate for expected outage duration
* [ ] Local disk capacity is sufficient
* [ ] Buffer behavior has been tested
* [ ] FortiAnalyzer receives buffered logs after recovery

> ⚠️ Changing the FAZ disk-buffer size can restart/reset `miglogd` behavior. Perform changes during an appropriate maintenance window when required.

# 7. Disk Buffer Overflow Checklist

A disk buffer has finite capacity.

### Normal behavior

```text
New Log
   |
   v
Buffer Available?
   |
  YES
   |
   v
Store Log
```

### Buffer Full

```text
New Log
   |
   v
Buffer Full
   |
   v
Oldest Data Removed
   |
   v
New Log Stored
```

This creates a FIFO-style overwrite behavior when the buffer is allowed to recycle old data.

### Example

```text
FAZ Disk Buffer
     |
     v
   200 MB
     |
     v
Buffer Full
     |
     v
Oldest Logs
     ↓
Replaced by Newer Logs
```

### Checklist

* [ ] Buffer size is known
* [ ] Expected FAZ outage duration is known
* [ ] Estimated log volume is known
* [ ] Buffer can absorb expected outage
* [ ] FIFO/overwrite behavior is understood
* [ ] Potential log-loss scenario is documented

### Disk-Full Behavior

```bash
config log disk setting
    set diskfull nolog
end
```

### Interpretation

```text
Disk Full
   |
   v
No additional local disk logging
```

### Trade-off

* [ ] Decide whether preserving existing logs is more important than accepting new logs
* [ ] Document disk-full behavior
* [ ] Monitor disk utilization
* [ ] Alert before storage exhaustion

# 9. UUID Logging Checklist

* [ ] Policy UUID logging enabled
* [ ] UUIDs appear in relevant logs
* [ ] SIEM correlation uses UUID where appropriate
* [ ] Automation references stable object identifiers
* [ ] Configuration changes can be correlated with historical logs

### Why UUID?

```text
FortiGate Object
      |
      v
    UUID
      |
      v
Firewall Policy
      |
      v
     Log
      |
      v
FortiAnalyzer / SIEM
```

### UUID Use Cases

* [ ] Log correlation
* [ ] SIEM integration
* [ ] API automation
* [ ] Configuration auditing
* [ ] Object tracking
* [ ] Policy correlation

> **Practical rule:** Human-readable object names can change; UUIDs provide a stronger correlation key for automation and historical analysis.

# 10. Free-Style Filter Checklist

Free-style filtering is useful when structured filtering is not sufficient.

### Basic syntax

```bash
execute log filter free-style "..."
```

### Filter by Log ID

```bash
execute log filter free-style "logid 0102043039 0102043040"
```

### Filter by Source IP

```bash
execute log filter free-style "srcip 192.168.2.5 192.168.2.205"
```

### OR Condition

```bash
execute log filter free-style "(logid 0102043039) or (srcip 192.168.2.5 192.168.2.205)"
```

### AND Condition

```bash
execute log filter free-style "(srcip 192.168.2.5) and (dstip 10.10.10.10)"
```

### Verify Active Filter

```bash
execute log filter dump
```

### Display Logs

```bash
execute log display
```

### Checklist

* [ ] Correct log device selected
* [ ] Correct category selected
* [ ] Free-style filter syntax validated
* [ ] Log ID condition verified
* [ ] Source IP condition verified
* [ ] Destination IP condition verified
* [ ] `AND` / `OR` logic verified
* [ ] Active filter dumped
* [ ] Resulting logs reviewed

## The Logging Troubleshooting Model

```text
             LOGGING PROBLEM
                    |
          +---------+---------+
          |                   |
       GENERATION          DELIVERY
          |                   |
          v                   v
      Log Exists?          FAZ Reachable?
          |                   |
          v                   v
       Local Log           Forwarding
          |                   |
          v                   v
       miglogd            Buffering
          |                   |
          +---------+---------+
                    |
                    v
                STORAGE
                    |
                    v
               ANALYSIS
                    |
                    v
               CORRELATION
```

> **Golden Rule:** Do not start by blaming FortiAnalyzer. First determine whether the log was **generated, processed, buffered, forwarded, stored, and finally ingested**.
