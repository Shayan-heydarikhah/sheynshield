    what is the differences  between cdn and adn?
        they are same but 
        have much in common, including performance benefits, on-demand pricing, security and availability.they also share many techniques, including tcp optimization, load balancing and cache

        cdns work by storing digital content that is often accessible in geographically distributed locations
            if your website does not have a heavy performance / interactive application, cdn will be your best bet not only on performance but also on cost-effectiveness for your organization.
        
        adn is a combination of features that provide program access, security, visibility and acceleration
            if your website is constantly evolving or acting as an interactive terminal to web-based software, adn is an ideal candidate.
            
            remember that adn is not yet a common term, so some cdn products may actually be dna. be careful and be sure to ask questions before making a decision

    fpga :    
        field programmable gate arrays
        hardware  base scalability
        are semiconductor devices that are based around a matrix of configurable logic blocks (clbs)
        this feature distinguishes fpgas from application specific integrated circuits (asics)
        one-time programmable (otp)
        fpgas used to be selected for lower speed/complexity/volume designs in the past, today’s fpgas easily push the 500 mhz performance barrier. with unprecedented logic density increases and a host of other features, such as embedded processors, dsp blocks, clocking, and high-speed serial at ever lower price points

    owasp automated threat events (oat) & f5 asm/waf countermeasures
        introduction & overview  
        from version 14 onwards, f5 provides solutions for several of these oats  
        using a microservices architecture under the bot profile, we can configure countermeasures for 9 of these threat types



        oat-001 » carding  
        (also known as: card stuffing, credit card stuffing, card verification)  

        description:  
          involves stolen payment card data

        mitigation:  
          dynamic passwords (otps) and multi-factor mechanisms are used to prevent automated carding attempts

        suggested countermeasures:  
          handled via asm capabilities and otp verification workflows



        oat-002 » token cracking  
        (also known as: coupon guessing / voucher enumeration / gift card enumeration / discount enumeration)  

        description:  
          websites sometimes offer discount codes or vouchers the generation logic must ensure these tokens are not easily predictable

        developer measures:  
          implement access filters (require user authentication before validation)  
          require activation codes  
          rate-limit and track time intervals between failed attempts



        oat-003 » ad fraud  
        "false clicks and fraudulent display of web-placed advertisements"  

        description:  
          websites may contain ads or pop-ups these can be legitimate developer implementations (redirection or closing) or malicious injections

        script execution mechanics & xss:  
          server-side languages (php) render on the server, get parsed, and send pure html to the browser  
          javascript executes directly inside the client’s browser  
          if a hacker pushes a script to the server, it will execute in the client’s browser — this is cross-site scripting (xss)

        mitigation:  
          securing the system against xss and rce prevents malicious responses from reaching the client



        oat-004 » fingerprinting  
        "elicit information about supporting software, framework types, and versions"  

        description:  
          attackers use footprinting/fingerprinting to identify server technologies and find known vulnerabilities

        mitigation:  
          prevent information leakage (hide server header details)  
          use attack signatures on the waf to block reconnaissance attempts  
          implement ltp (local traffic policies) and irules to rewrite, remove, or replace content in http responses  
          ensure no server version details or internal metadata leak through the waf



        oat-005 » scalping  
        "obtain limited-availability and/or preferred goods/services by unfair methods"  

        description:  
          a single user accesses a website through multiple accounts to exhaust special offers and discounts

        mitigation:  
          handle via asm, tps (transactions per second) limits, bot defense, and developer logic  
          utilize the dos engine to monitor and enforce rate limits  
          apply bot detection to determine whether requests originate from a headless browser



        oat-006 » expediting  
        "perform actions to hasten progress of usually slow, tedious, or time-consuming actions"  

        description:  
          includes slow header, slow post, and slow get attacks attackers consume server resources by transmitting requests extremely slowly to keep connections open

        mitigation:  
          developer: limit http header field timeouts  
          waf (ltm/awf modules): enable eviction policies with strategies such as “bios slow” to identify and purge low-activity connections



        oat-007 » credential cracking  
        "identify valid login credentials by trying different values for usernames and/or passwords"  

        description:  
          attackers use trial-and-error with dictionary lists of common username/password combinations

        mitigation:  
          enforce complex password policies and avoid usernames based on personal names  
          waf layer: apply character filters on input fields  
          restrict failed login attempts per user, session, or geo-location  
          use asm brute force protection



        oat-008 » credential stuffing  
        "mass log-in attempts used to verify the validity of stolen username/password pairs"  

        description:  
          unchecked credential stuffing often leads to successful credential cracking

        mitigation:  
          mandate periodic password changes and strong password rules  
          f5 maintains an updated credential stuffing database with billions of compromised credentials  
          developers should enforce strong password policies on registration pages



        oat-009 » captcha defeat  
        "solve anti-automation tests"  

        description:  
          automated bots use ocr and solving databases to bypass text captchas

        f5 protection capabilities:  
          f5 can dynamically generate captcha as an enforcement action without requiring application code changes  
          audio captcha is supported from version 15 onwards

        proactive vs reactive defense:  
          proactive: every request is assumed to be a bot until proven otherwise (js challenges + random questions)  
          reactive: traffic is allowed first; if high failure rates or spikes occur, captcha or blocking is triggered



        oat-010 » card cracking  
        "identify missing start/expiry dates and security codes for stolen payment card data by trying different values"  

        description:  
          similar to credential cracking, but targets missing payment card details (cvv, expiration date)



        oat-011 » scraping  
        "collect application content and/or other data for use elsewhere"  

        description:  
          known as web scraping f5 included gui configuration from version 11 and converted it to a microservice architecture in version 14+

        impact:  
          used for commercial extraction or resource exhaustion

        waf detection & mitigation:  
          monitor requests under a specific host/url from a single source ip  
          actions include: js challenge, captcha, http redirect, reset connection, or honeypot



        oat-012 » cashing out  
        "buy goods or obtain cash utilizing validated stolen payment card or other user account data"  

        description:  
          unauthorized transactions using stolen accounts/cards

        mitigation:  
          require secondary activation codes (otp) within a limited time window before high-value actions



        oat-013 » sniping  
        "last-minute bid or offer for goods or services"  

        description:  
          similar to oat-005, targeting limited-time discounts or special offers

        mitigation:  
          prevent single source ips from repeated logins or multi-account access  
          enforce strict rate limiting and bot detection



        oat-014 » vulnerability scanning  
        "crawl and fuzz application to identify weaknesses and possible vulnerabilities"  

        description:  
          automated scanners probe applications basic tools are identified via user-agent

        evasion & mitigation:  
          advanced tools spoof valid browser user-agents  
          deploy js challenges and captchas  
          keep waf attack signatures updated using f5 threat campaign licenses



        oat-015 » denial of service (dos)  
        "target resources of the application and database servers, or individual user accounts, to achieve denial of service"  

        types:  
          value metric attacks, resource dos, and cache poisoning dos (cp dos)

        cache poisoning dos:  
          4xx and 5xx error responses get cached by proxy/cdn servers

        mitigation:  
          prevent http 4xx/5xx error codes from being cached  
          prevent information leakage via error messages  
          developers must suppress raw error codes and handle them gracefully



        oat-016 » skewing  
        "repeated link clicks, page requests or form submissions intended to alter some metric"  

        description:  
          distorting application statistics (artificially shifting peak usage metrics)

        impact:  
          misleads capacity planning and operational policies

        mitigation:  
          enforce strict user authentication and rate verification at the application level



        oat-017 » spamming  
        "malicious or questionable information addition that appears in public or private content, databases or user messages"  

        description:  
          unsolicited content submission via forms, comments, or messaging systems

        mitigation:  
          do not return full diagnostic responses to unverified requesters  
          train personnel against clicking unknown links/emails  
          enable dos attack protection, csrf protection, and bot detection in f5 policies



        oat-018 » footprinting  
        "probe and explore application to identify its constituents and properties"  

        description:  
          unlike scraping, footprinting is an enumeration of the application itself (tools like burp suite)

        core rule:  
          http 4xx and 5xx error codes must never be returned directly from the server to an attacker



        oat-019 » account creation  
        "create multiple accounts for subsequent misuse"  

        description:  
          automated creation of mass accounts for future exploitation

        mitigation:  
          validate user identity, enforce email/sms verification, and ensure authenticity of registration data



        oat-020 » account aggregation  
        "use by an intermediary application that collects together multiple accounts and interacts on their behalf"  

        description:  
          intermediary tools aggregating control over multiple user accounts

        mitigation:  
          ensure strict 1:1 mapping between real users and accounts, enforce explicit privileges, and disallow duplicate credentials



        oat-021 » denial of inventory  
        "deplete goods or services stock without ever completing the purchase or committing to the transaction"  

        description:  
          holding items in shopping carts or download queues to exhaust stock or bandwidth without paying

        mitigation:  
          enforce cart timeouts and reservation limits to prevent locking of resources

    owasp top 10 application security risks
        overview  
        a1 | a2 | a3 | a4 | a5 | a6 | a7 | a8 | a9 | a10



        risk 1: injection attacks (a1)  

        description:  
          an attacker can push a command, query, or code to the server if the developer has not properly performed input validation or input sanitization this can lead to a server-side risk if properly configured, we can prevent up to 70% of web-based attacks

        how the attack works:  
          an attacker injects a command, query, or code into a vulnerable element of the application  
          the web application server executes the injection  
          the attacker gains unauthorized access, causes a denial of service, or steals sensitive data

        asm/awf mitigation solutions:  
          attack signatures  
          meta character restrictions (parameter name/value)  
          parameter restrictions (repeated occurrences, parameter length)  

          enabling attack signatures is one of the available solutions for injection the next option relates to input validation or input sanitization, where we can prevent these attacks by setting restrictions on characters and parameters



        risk 2: broken authentication attacks (a2)  

        description:  
          these attacks carry lower risk compared to injections and point to cases where the developer has implemented the service code in a way that allows a client to access an object without going through an authentication phase

        common attack techniques:  
          brute force / credential stuffing  
          session hijacking / session fixation  
          cross-site request forgery (csrf)  
          execution after redirect (ear)

        asm/awf mitigation solutions:  
          session hijacking protection and user sessions tracking  
          brute force / credential stuffing protection  
          csrf protection



        risk 3: sensitive data exposure attacks (a3)  

        description:  
          a sensitive data exposure flaw can occur when you:  
          store or transit data in clear text (most common)  
          protect data with an old or weak encryption  
          do not properly filter or mask data in transit  

          this points to situations where systems may contain sensitive data (national id numbers) that should not leave the system, but due to various reasons, the data is sent in plain text without hashing all these cases can lead to a man-in-the-middle (mitm) attack

        organizational perspective:  
          1 ensuring data does not leave the organization at all (data guard)  
          2 preventing man-in-the-middle attacks (requires https communication)

        sensitive parameters feature:  
          sometimes even the waf administrator should not have access to sensitive information in this case, the “sensitive parameters” feature is used the service owner must specify which parameters are sensitive so they will not be displayed in logs and the device gui

        asm/awf mitigation solutions:  
          ssl profiles (client-side / server-side)  
          http strict transport security (hsts) → enforcing https redirection  
          data guard  
          mask credit card numbers in request log  
          sensitive parameters



        risk 4: xml external entity (xxe) attacks (a4)  

        description:  
          xml and json are two widely used apis more than 80% of apis use json and rest xml is less frequently used due to its human readability and parsing overhead xxe attacks target weakly configured xml parsers

        possible impacts of successful xxe:  
          data disclosure and services access  
          denial-of-service (dos)  
          port scanning / remote code execution

        prevention methods:  
          restrict external entities  
          disallow external links  
          limit maximum xml size and number of elements  
          enable relevant attack signatures

        asm/awf mitigation solutions:  
          disallowing dtds (document type definitions)  
          enabling xxe attack signatures  
          external entity injection attempt  
          xml external entity (xxe) injection attempt (content)



        risk 5: broken access control (authorization) attacks (a5)  

        description:  
          unauthorized access to sensitive information  
          inappropriate creation or deletion of resources  
          user impersonation  
          privilege escalation  

          this risk refers to whether a user can access resources without completing a successful login process on websites requiring authentication, the user must first be authenticated this is primarily the developer’s responsibility using a session id, but part of the control can be handled on the waf

        urls flow enforcement:  
          there is an entry login page and an exit logout page we define a series of urls between login and logout, meaning only users who passed the initial login page can access those specific urls

        how does the waf detect a successful login?  
          we enter the access validation phase and ask the developer what event signifies a successful login (specific response code, content value, location header, or value in the response body)

        two common scenarios after access validation:  
          1 non-sequential access: multiple urls behind the login page where sequence does not matter (online banking)  
          2 sequential access: order matters (viewing page 1 first, then page 2)

        asm/awf mitigation solutions:  
          allowed and disallowed urls  
          urls flow enforcement  
          disallowed file types  
          attack signatures for “path traversal” and “predictable resource location”



        risk 6: security misconfiguration attacks (a6)  

        description:  
          this risk is not necessarily an active attack by itself, but it remains a critical risk area if a waf appliance is misconfigured, it can lead to any of the risks from a1 to a10

        examples of misconfiguration impact:  
          brute force / credential stuffing / forceful browsing  
          code injection / buffer overflow / command injection  
          cross-site scripting (xss)

        critical configuration areas:  
          urls  
          parameters  
          file types  
          headers  
          redirection domains  
          violation flags  
          brute force  
          credential stuffing

        asm/awf mitigation solutions:  
          do not use vendor-supplied defaults for system passwords and other security parameters  
          enabling secure password policy  
          protect all systems against malware and regularly update software  
          configuring all of the needed asm entities (allowed/disallowed objects)  
          enabling attack signatures / threat campaigns  
          requesting the customer/client to fill out a service questionnaire



        risk 7: cross-site scripting (xss/css) attacks (a7)  

        description:  
          cross-site scripting occurs when a web application receives untrusted data and then sends that data, without validation, to an end user’s web browser this enables an attacker to send executable code to the victim’s browser

        possible impacts:  
          session hijacking  
          defacing the website  
          redirecting the user to a site with malicious intent (most common)

        xss vs csrf:  
          in xss, the client trusts the server (attacker injects script that gets stored and later executed in another user’s browser)  
          in csrf, the server trusts the client (an infected client abuses the server’s trust using the session cookie)

        asm/awf mitigation solutions:  
          enabling xss attack signatures → cross site scripting signature set  
          enabling evasion technique detection → learning and blocking settings  
          setting the global “httponly” cookie attribute → system variables  
          defining acceptable parameter characters and definitions → parameter value type



        risk 8: insecure deserialization attacks (a8)  

        description:  
          “serialization” occurs when an application converts data structures and objects into a different format (binary, xml, json) “deserialization” is the reverse process attackers typically tamper with the data in data structures or objects

        possible impacts:  
          denial-of-service (dos) attacks  
          authentication bypasses  
          remote code execution attacks

        common scenario:  
          data is populated into arrays and sent to the server via get, put, or post insecure deserialization risks can manifest during this process

        asm/awf mitigation solutions:  
          json/xml validation → profiles / signature checks  
          http header validation → base64 decoding/normalization / signature checks  
          attack signatures → buffer overflow / command execution / denial of service / server side code injection



        risk 9: using components with known vulnerabilities (a9)  

        description:  
          using components with known vulnerabilities makes your application susceptible to attacks that target any part of the application stack (outdated wordpress installations)

        common attack types:  
          code injection / command injection  
          buffer overflow  
          cross-site scripting (xss)

        asm/awf mitigation solutions:  
          regularly audit software components and their dependencies  
          regularly update software and attack signature sets  
          regularly scan software components and their dependencies → virtual patching  
          install software components from known sources



        risk 10: insufficient logging and monitoring (a10)  

        description:  
          insufficient logging, monitoring, and reporting make your application susceptible to attacks this risk is critical regarding attack logs logging may fail or report inadequately due to outdated operating systems or configurations

        possible resulting attack types:  
          code injection / command injection  
          buffer overflow / forceful browsing  
          cross-site scripting (xss)

        asm/awf mitigation solutions:  
          configuring big-ip asm logging profiles  
          filtering your desired logging information  
          setting attack “alarm” and “blocking” logging  
          viewing event correlation → event logs
